## Findings that change the plan

- **KDE Partition Manager does not repair GPT headers.** kpmcore has zero
  GPT header code; `sfdisk` (libfdisk) silently falls back to the backup
  header and rewrites both on the next write. Explicit, diagnosed repair is
  something only `gdisk`/`sgdisk` do today. It stays a v1 requirement (R6)
  and is now a differentiator rather than parity.
- **All three GUI tools are thin layers over external tools.** GNOME Disks
  → UDisks2 → libblockdev → `mkfs.*`/`fsck.*`/libfdisk/cryptsetup; kpmcore →
  ~90 whitelisted binaries through a root D-Bus helper; GParted → libparted +
  ~60 binaries. None owns on-disk logic. The in-process requirement (R8) is
  therefore a genuine gap, not a reimplementation of what exists.
- **Nothing in the three tools is borrowable as code** (GPL-2+/GPL-3+). The
  borrowable *code* comes from elsewhere: FreeBSD `sys/geom/part/*` (BSD-2:
  MBR/EBR/GPT/APM/BSD/LDM read+write), FatFs (BSD-1: FAT/exFAT r/w),
  lwext4's BSD-3 files (ext4 read), tc-play (BSD-2: TrueCrypt/VeraCrypt
  headers), FreeBSD `newfs_msdos`/`fsck_msdosfs`. LGPL libraries (libext2fs,
  libfuse, Dokany, libyal family) are allowed as optional dynamic backends.
- **GNOME Disks' Rust port** is a 1:1 D-Bus client port, not a storage
  library, and the ported estimator has a bug that makes it record no
  samples. Nothing there is useful to us.
- **GParted's `struct FS` with a "how" enum per operation** and kpmcore's
  `CommandSupportType` are the same idea; it is adopted as our run-time
  `Capabilities` bitset plus a provider registry that lets in-process and
  external-tool implementations coexist with priorities.
- **FUSE-T on macOS is proprietary** and WinFsp's GPL exception excludes
  proprietary downstream users; the plan is Dokany (LGPL) on Windows,
  WinFsp optional, and an own NFS-loopback server as the kext-less macOS
  path.

## Design decisions taken (owner to confirm)

- Chain of ~13 CMake libraries, not one (`design/10` §1–2).
- Abstract base classes + capability objects; single inheritance only;
  no virtual inheritance (`design/11`).
- `Expected<T>` error returns, no exceptions across library boundaries.
- Our own `.stein` image container (chunked, compressed, hashed, split,
  resumable, used-block-aware) plus raw/split-raw in v1, E01/VHD/qcow2
  readers in v2 (`design/14`).
- Privileged helper with typed RPC, never a generic command runner
  (`design/16` §3).

## Open questions for the owner

1. Which UI first in M2: GTK4 Linux (fastest to validate on CI), or macOS
   (where Disk Utility is losing features), or Windows (worst incumbent)?
2. C++20 with a small `Expected` polyfill, or require C++23 for
   `std::expected`?
3. Project name for the user app: keep "Dr. Stein"?
4. Should M1 include the optional `stein_backend_exec` (wrappers around
   `mkfs.*` etc.) so Linux users get resize/format on day one, or hold it to
   M3 to keep pressure on native implementations?
5. Are LGPL dynamic backends (libext2fs for ext4 write in v1) acceptable, or
   must v1 be MIT/BSD-only?
