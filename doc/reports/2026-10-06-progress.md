## Verified against the reference tools

- Our GPT writer reproduces `sgdisk`'s headers, entry arrays and protective
  MBR byte for byte (including the real CHS values sgdisk puts in the PMBR).
- Our MBR writer reproduces `sfdisk`'s MBR and EBR sectors byte for byte.
- After `stein repair` on an image with a zeroed primary header, `sgdisk -v`
  reports "No problems found".
- `stein pt dump` + `stein pt restore` brings a GPT with both headers
  destroyed back to a table sgdisk accepts — the R5a "restore only the
  table" scenario, 5 small regions instead of the whole disk.

## Design points settled while coding

- Tables are edited in memory; `write()` always places the backup at the
  end of the *target* device, which is what makes "restore to a larger disk"
  and "repair after growth" the same code path.
- `repair()` refuses to write when neither copy of the entry array is
  intact, rather than writing an empty table.
- Field tables come from manifests (`formats/*.layout.toml`); offsets appear
  exactly once. The generated classes are plain and debuggable.
- ASan caught one real bug during development (pointer into a vector that
  reallocated); sanitizers stay on in the debug preset and in Linux CI.

## Later: `stein_ops` — plan, preview, apply on the real code path

The design in `design/13-operations.md` said the preview should not be a
parallel model of what the jobs *would* do. It now is not: `OverlayDevice`
(`stein_block`) is a copy-on-write device over the target; an
`OperationStack` runs each operation's jobs against the overlay and
re-probes the overlay for the preview. `apply()` writes the overlay's dirty
blocks to the device in one ordered pass, re-probes, and reports whether the
device matches the preview. A failing job rolls the overlay back; `pop()`
replays the remaining operations on a fresh overlay.

Operations so far: `CreateTable` (GPT/MBR/APM; zeroes old table copies and
whole-device filesystem signatures first), `AddPartition` (optionally wipes
stale signatures in the new range), `DeletePartition`, `UpdatePartition`
(type/name/bounds), `RepairTable`, `WipeSignatures`. `signatureRegions()`
derives what to zero from the probe tree (first MiB, every metadata region
the detectors reported, last MiB).

CLI: `stein pt create|add|rm|set|wipe`, each printing the pending list, the
bytes it would touch and the resulting tree; `--dry-run` stops there,
destructive edits on a real block device need `--force`. A create/add/set
sequence on a 64 MiB image gives a table `sgdisk -v` finds no problems with.

Windows CI: compiles; the remaining failure was DLLs not found by the test
executables (fixed by one `bin/` output directory).

## Later: used-block-only imaging (L1)

`fs::AllocationMap` plus `FileSystem::allocationMap()` for ext2/3/4 (group
descriptor block bitmaps), FAT12/16/32 (FAT entries), exFAT (allocation
bitmap file through the root directory), NTFS (`$Bitmap` via the MFT run
list) and HFS+ (allocation file extents). Dirty filesystems and ext journals
needing recovery refuse, so a stale bitmap never drops data. The copy engine
zeroes free blocks of mapped filesystems, so whole-free chunks become zero
chunks and partially used chunks compress to their used part; the manifest
records `used_blocks_only`. `stein image create --used-only`, and profiles
default to it (`image.used_only`).

Fixtures `tests/fixtures/alloc/` are real `mkfs` outputs with files written
through loop mounts; the test asserts that **every non-zero byte on the
device lies in a block the map calls used** and that free counts equal
`dumpe2fs`, `fsck.fat` and `ntfsinfo`. On a 64 MiB ext4 with 8 MiB of junk in
free space, the image went from 8.5 MB to 140 KB, `e2fsck -fn` is clean after
restore and the files' checksums match.

## Later: encrypted images (R5e)

`stein_core` gained ChaCha20-Poly1305, HMAC-SHA256, PBKDF2-HMAC-SHA256 and OS
randomness (own code; known-answer vectors from the Python `cryptography`
package and RFC 8439; tamper tests). `.stein` images can now be encrypted:
a plaintext key area with up to eight passphrase slots wraps one random
master key (LUKS2 shape, `doc/spec/stein-image-v1.md` §Encryption); the
manifest, every chunk and the image hash are protected, while structure and
per-chunk stored CRCs stay verifiable without the key. `stein image create
--passphrase`, `stein image keys list|add|remove`, `--passphrase`,
`--passphrase-file`, `$STEIN_PASSPHRASE` or a no-echo prompt everywhere an
image is opened; profiles set `image.encrypt` and never store the passphrase.
Decision D16 records why ChaCha20-Poly1305 and not AES-GCM/XTS.

Also since the last section: `Platform::unmount()` on Linux/macOS, Windows
volume lock + dismount on exclusive open, and the restore scenario unmounts
or refuses while the target's volumes are mounted.

## Later: encrypted pieces and media tests

## Later: LUKS opened in-process (the flagship goal's first half)

`stein_container` parses LUKS1 and LUKS2 headers, unlocks a key slot with a
passphrase (PBKDF2 with sha256/sha1 or Argon2id/Argon2i, AES-XTS-decrypted
key material, anti-forensic merge, master-key digest check) and presents
the payload as a `BlockDevice` that decrypts per sector (aes-xts-plain64,
512 or 4096-byte sectors, `iv_tweak`). AES comes with AES-NI and ARMv8
kernels. Fixtures were formatted by `cryptsetup` and their payload encrypted
by the Python `cryptography` package under the dumped master key, so the
test compares our recovered master key with cryptsetup's and probes the
inner ext2. `stein probe --passphrase` shows the plaintext under the
container; `stein luks info|unlock|extract` inspect, check and decrypt into
a plain image, on any OS: this is the step before mounting an ext4-in-LUKS
on Windows or macOS.

## Later: LVM2 logical volumes (the other half of "ext4 in LVM in LUKS")

`stein_volume` reads a PV's text metadata (including the wrapped circular
buffer), parses LVM's config grammar into a volume group model and
assembles logical volumes as devices: linear and multi-segment volumes via
slices and `ConcatDevice`, striped volumes via a round-robin
`StripedDevice`; mirror/raid/thin/cache segments are reported, not mapped.
PVs are added one by one; a volume maps once every PV it touches has been
seen. Fixtures come from lvm2 itself (`--driverloaded n`, no activation),
with filesystems written at the extent offsets `lvs` reports, so the test
reads `lv_linear`, `lv_frag` (two segments) and `lv_striped` (two PVs) back
through our mapping. `stein probe` lists a PV's volumes and probes the
mappable ones; `stein lvm list|extract` shows the group and copies a volume
into a plain image.

## Later: reading files in-process (L3 for ext2/3/4)

`fs::Reader` (root, lookup, stat, readdir, read, readlink) and an ext2/3/4
implementation: extent trees and indirect blocks, inline data, linear /

## Later: NTFS reader

## Later: mounting any reader through FUSE (R5d on Linux)

`stein_mount`: an `fs::Reader` becomes a read-only filesystem the OS can
browse. The Linux backend is libfuse3 (LGPL, linked dynamically, optional
at configure time: without `pkg-config fuse3` a stub reports
`Unsupported`). High-level FUSE operations getattr/readdir/open/read/
readlink/statfs over a path → inode cache, one thread, no writes
(`EROFS`), `allow_other` on request. `stein mount <image|device> <dir>
[--part N] [--passphrase ...] [--lv NAME]` mounts a partition from inside
an image, a LUKS container or an LVM volume the same way `stein ls` reads
it; `fusermount3 -u` or `umount` ends the loop cleanly, and `Mount::stop()`
does the same from inside a program. The test mounts the ext4 fixture
in-process and compares every file hash, directory and symlink with the
kernel-mount oracle through plain `std::ifstream` /
`std::filesystem` calls, then checks that creating a file fails.

One real lesson is encoded in `stop()`: `fuse_exit()` alone does not wake
a loop blocked in `read()`, and libfuse drops a request it reads after
the exit flag is set, so a process that pokes its own mountpoint to wake
the loop deadlocks in the kernel for good (uninterruptible, only
`/sys/fs/fuse/connections/*/abort` frees it). Unmounting is the only
clean wake-up; the loop then ends with `ENODEV`, which libfuse treats as
a normal exit.

macOS builds the stub for now; the kext-less NFS loopback backend from
design doc 15 is the next step there. Windows: see below.

## Later: exFAT reader

Boot-sector geometry, 32-bit FAT chains and contiguous `NoFatChain`
streams, directory entry sets (File + Stream Extension + File Name),
`ValidDataLength`-aware reads, timestamps with their UTC-offset byte, and
case-insensitive lookup through the volume's own (run-length compressed)
up-case table, so `ünïcödé` matches `ÜNÏCÖDÉ` the way the format defines
it. The container has no kernel exfat driver, so the fixtures are written
with exfat-fuse over a loop device (`tools/fixtures/make_exfat_fixtures.sh`,
4 KiB and 32 KiB clusters, a deliberately fragmented file, 255-character
and Unicode names, a 300-entry directory) and checked by `fsck.exfat`;
every entry, size and SHA-256 matches. `resolvePath` now keeps an ancestor
stack for `..` instead of expecting a dot-dot directory entry, which exFAT
(like NTFS and HFS+) does not have. Four readers (ext, NTFS, FAT, exFAT)
cover every filesystem a camera card, a USB stick or a Windows or Linux
system disk is likely to carry; all of them mount through `stein mount`.

## Later: HFS+ / HFSX reader, with fixtures built on macOS

The fixture problem first: the Debian `hfsplus` tools reject volumes made
by `mkfs.hfsplus` and there is no kernel driver in the build container, so a
small workflow (`.github/workflows/fixtures-macos.yml`) builds the images on
the macOS runner with `hdiutil` and the native driver, fills them with the
same deterministic tree as the other readers plus hard links and names that
differ only in case, records the oracle with a portable `oracle.py`, and
commits the result to the branch (artifact downloads are blocked from some
environments). Three variants: HFS+, case-sensitive HFSX and journaled HFS+.

The reader (TN1150): volume-header forks, B-tree header/index/leaf nodes,
catalog folder, file and thread records, the extents overflow tree for forks
with more than eight extents, hard links resolved through the `iNode` files
in the private metadata folder (link counts included), `S_IFLNK` symlinks,
the journal files and private folders hidden the way the kernel hides them,
case-insensitive lookup for HFS+ and binary for HFSX. Catalog searches use
only the parent-id part of the key order, so no copy of Apple's case-folding
table is needed for listings; the test compares every entry, SHA-256,
symlink target, the hard-link count of three and the stored mtime for all
three variants. Five readers now: ext, NTFS, FAT, exFAT, HFS+.

## Later: ISO 9660 reader

Primary and supplementary volume descriptors, directory records with
both-endian fields and multi-extent files, Rock Ridge SUSP entries (`SP`,

## Later: VeraCrypt and TrueCrypt volumes

`container::Tcrypt` opens VeraCrypt and TrueCrypt volumes the only way the
format allows: there is no signature, so each candidate header (primary,
hidden at 64 KiB, and the two backup copies at the end) is decrypted with
the passphrase through PBKDF2-HMAC-SHA-512 or SHA-256 (VeraCrypt, with the
PIM iteration multiplier; TrueCrypt's 1000-iteration SHA-512) and AES-XTS,
and accepted when the magic and both CRC-32s check out. The payload is the
same XTS device LUKS uses, with the absolute 512-byte data-unit number as
tweak. SHA-512 joined the core hashes for this, and the generic HMAC/PBKDF2
is now allocation-free (the 500 000-iteration default takes well under a
second in release). Cheap headers are tried first, so a TrueCrypt probe
never pays VeraCrypt's price. Fixtures are generated by an independent
Python implementation of the format (`cryptography` XTS, hashlib PBKDF2)
around debugfs-filled ext2 payloads: default-PIM SHA-512, SHA-256 with PIM
3, TrueCrypt, and an outer+hidden pair; the test opens each, reads the file
inside, rejects a wrong passphrase, and opens the volume from its backup
header after the primary one is overwritten. `stein probe --passphrase`
now descends into such volumes, `stein ls|cat|cp|mount` read through them,
and `stein tcrypt unlock|extract` work like their LUKS counterparts.
Cascades (Serpent, Twofish, Camellia, Kuznyechik), Whirlpool/Streebog
and system encryption are reported as unsupported rather than guessed at.
RIPEMD-160 (TrueCrypt's default PRF, and VeraCrypt's before 1.26 with its
655 331 iterations) and BLAKE2s-256 (VeraCrypt 1.26+) joined the PRF list
later, as core hashers checked against Python for digests, HMAC and
PBKDF2, with fixtures for each.

## Later: XFS reader

Superblock geometry, v2/v3 inodes with `bigtime` and `nrext64` handled,

ISO 9660, XFS. btrfs is next (`mkfs.btrfs --rootdir` gives fixtures the
same way).

Superblock and chunk tree for the logical-to-physical map (SINGLE, DUP,
RAID1 and RAID0/10 striping; RAID5/6 refused), the root tree for subvolume

browsed, copied from and (on Linux) mounted, from inside any image, LUKS or

## Later: virtual-disk containers (qcow2, VHD, VHDX, VMDK, VDI) and a DEFLATE decoder

A VM disk is a disk: `image::openVdisk` presents qcow2 (v2 and v3,
deflate-compressed clusters, explicit zero clusters), VHD (fixed and
dynamic, BAT plus sector bitmaps), VHDX (header selection by sequence and
CRC32C, region and metadata tables, BAT with chunk-ratio bitmap entries, a
log that must be empty), VMDK (sparse extents, stream-optimized compressed
grains with their markers and footer, plain-text descriptors with SPARSE,
FLAT and ZERO extents concatenated) and VDI (dynamic and fixed block maps)
as read-only block devices, so `stein probe|ls|cat|cp|mount|image create`
work on them unchanged. Backing files, snapshot and differencing chains,
encryption and zstd are reported rather than guessed at. The decoder they
need, raw DEFLATE with the zlib and gzip wrappers (RFC 1950/1951/1952), is
our own ~300 lines in `core::compress`, checked against Python's zlib on
stored, fixed-Huffman, dynamic-Huffman, raw and gzip streams; it will serve
E01 and DMG next. Fixtures: one raw disk (GPT with a FAT12 and an ext2
partition) converted by `qemu-img` into ten variants; the test opens each,
hashes the whole virtual disk against the raw source, reads odd-sized
windows across cluster boundaries, probes the partition table and reads
the ext2 label through the container.

## Later: E01 / EWF forensic images

The same container module reads EnCase 5 and 6 (EWF version 1) evidence
files: the 13-byte segment header, the section chain with its Adler-32
checksums, `volume`, `sectors` and `table` sections (base offset plus
31-bit entries with the compression flag; chunk sizes from the next entry
and the section end), zlib-compressed chunks and uncompressed chunks with
their trailing checksum, segment files `.E01`…`.E99`, `.EAA`…, and the
stored MD5/SHA-1 from the `hash`/`digest` sections exposed in `VdiskInfo`.
Fixtures are acquired with libewf's `ewfacquire` from the same kind of
raw GPT disk: EnCase 6 best compression, EnCase 6 uncompressed split into
13 segments, EnCase 5; the test rebuilds the raw disk byte for byte,
checks that our MD5 of it equals the acquirer's stored digest, and probes
the partitions through the image. EWF2 (EnCase 7), SMART and logical
evidence files are recognised as not supported.

## Later: Apple DMG images

UDIF images join the container module: the `koly` trailer, the XML
property list's `blkx` resources (every `mish` block found by decoding the
`<data>` elements, no plist parser needed), chunk tables with raw, zero,
ignored, zlib and ADC blocks. ADC (Apple Data Compression, the UDCO codec)
is a 40-line decoder in `core::compress` next to inflate. Fixtures come
from the macOS workflow (`hdiutil convert` of the same raw GPT disk the
virtual-disk fixtures use, recovered from the fixed-VHD fixture) in UDRO,
UDZO and UDCO flavours; hdiutil marks the unpartitioned tail of the disk
as ignored, so the test compares the partition table and both partitions
byte for byte against the raw source rather than the whole disk. The
macOS generators now run only when their fixtures are absent, since
hdiutil output carries fresh UUIDs and would churn the repository.
A bzip2 decoder (`core::compress::bunzip2`: Huffman tables and selectors,
MTF/RLE2, inverse BWT, block and stream CRCs; checked against Python's
`bz2` on single and multi-block streams) followed for UDBZ images. lzfse
and lzma blocks, segmented sets and encrypted images are reported as
unsupported. Eight container formats now open as disks: .stein, qcow2,
VHD, VHDX, VMDK, VDI, E01, DMG. `stein image info` describes any of them.

## Later: UDF reader

ECMA-167 / OSTA UDF: the volume recognition sequence, anchor pointers for
the common block sizes, the volume descriptor sequence (partition and
logical volume descriptors, reserve sequence fallback), partition maps of
all three kinds (physical, sparable with its sparing tables, metadata

## Later: Windows mount through WinFsp

The Linux backend's source now also builds on Windows against WinFsp's
fuse3-compatible layer (`$ProgramFiles(x86)\WinFsp\inc`, `winfsp-x64.lib`):
the only platform seams are `fuse_stat`/`fuse_off_t` type names, uid/gid
from the FUSE context (WinFsp maps them to the caller's SID), and the mount
point rule (a free drive letter such as `X:` or an absent directory, not an
existing one). The DLL is delay-loaded and located through WinFsp's
registry key, so a binary built with WinFsp still runs on a machine
without it and `Mount::available()` says so. CI installs WinFsp from
chocolatey and the test picks a free drive letter, mounts the ext4 fixture
and reads every file through `std::ifstream` exactly as on Linux.
`STEIN_REQUIRE_MOUNT=1` turns the "no FUSE here" skip into a failure on
Linux and Windows so a broken backend cannot hide behind it.

Two WinFsp differences bit: `fuse_unmount()` there destroys the file
system object the loop thread is still dispatching on (on Linux it only
closes the kernel connection), so on Windows `stop()` just signals
`fuse_exit()` and `run()` unmounts after `fuse_loop()` returns; and
`std::filesystem::read_symlink` reports targets with backslashes, so the
test compares `generic_string()`.

## Later: btrfs compressed extents (zlib, lzo) and an LZO1X decoder

`compress::lzo1xDecompress` in `stein_core`: the LZO1X instruction set
(M1–M4 matches, literal runs, length extensions, the `17 0 0` end marker)
with the three decoding states the reference keeps (after a literal run,
after one to three trailing literals, after a bare match), bounds-checked
on both sides. Vectors from liblzo2's `lzo1x_999` and `lzo1x_1` on
generators the test reproduces (runs, raw literals, random bytes, 60 KiB
of text, matches beyond 16 KiB), plus truncated input and short buffers.

The btrfs reader decompresses zlib extents with `inflateZlib` and lzo
extents with btrfs's framing (a total-length word, then length-prefixed
segments that never decompress past one sector, with a length word that
would straddle a sector pushed to the next one). Inline and regular
compressed extents both work; `extent data offset` applies to the
decompressed bytes; the last decompressed extent is cached so sequential
reads are not quadratic. zstd extents followed an hour later (next
section). Fixtures: `mkfs.btrfs
--compress zlib|lzo|zstd` (btrfs-progs 6.14+, built from source here since
the distro ships 6.6; `MKFS_BTRFS=/path` points the script at it), with a
highly compressible 315 KiB file, a moderately compressible one and a
compressible inline extent added to the shared source tree; `btrfs check`
confirms every variant, the oracle is the source tree.

## Later: a Zstandard decoder; btrfs zstd extents and qcow2 zstd clusters

`compress::zstdDecompress` in `stein_core`, RFC 8878 from scratch: frame
headers (content size, window descriptor, checksum flag; dictionary frames
refused), raw/RLE/compressed blocks, literals as raw, RLE, Huffman with a
direct or FSE-compressed weight table in one or four streams, or treeless
(reusing the previous block's tree), sequences with predefined, RLE,
FSE-compressed or repeated tables, the three repeat offsets with the
literal-length-zero special case, skippable frames, concatenated frames,
and the XXH64 content checksum (own XXH64). `zstdDecompressFrame` stops
after the first frame for containers that pack frames back to back.
Vectors from the reference `zstd` CLI at levels 1, 3, 19 and `--ultra -22
--long=27`, with and without checksums, on inputs from one byte to 300 KiB
of text (several blocks, so repeat modes and treeless literals are hit),
plus concatenation, truncation, short buffers and a flipped byte.

With it the btrfs reader reads zstd extents (the `btrfs_zstd` fixture now
reads back in full like the others) and qcow2 opens images converted with
`compression_type=zstd` (new `qcow2_zstd` fixture from qemu-img). The
`.stein` format itself still uses LZ4; zstd as an image codec is a later
choice.

## Later: LZMA, LZMA2 and xz decoders; DMG ULMO blocks

`compress::lzmaDecompressRaw`, `lzmaDecompress` (.lzma), `lzma2Decompress`
and `xzDecompress` in `stein_core`: the LZMA range coder and its literal,
match, repeat-match and short-repeat models with the state machine from
the reference, LZMA2 chunks (uncompressed, state/properties/dictionary
resets) and the .xz container (stream header and footer, block headers
with LZMA2 as the only accepted filter, CRC32/CRC64/SHA-256 block checks,
the index checked against the blocks, concatenated streams with padding).
Streams without a known size end on the end marker; when the buffer
fills first the next symbol decides between "exactly right" and "too
small". BCJ and delta filter chains are refused with `Unsupported`.
Vectors from XZ Utils 5.4.5: presets 0/6/9e with each check type, 64 KiB
multi-block files, `--check=none`, `.lzma`, raw LZMA1, concatenated
streams, truncation, short buffers and a flipped range-coder byte, which
the reference also rejects because a chunk's range coder must end on zero.

DMG `ULMO` blocks (0x80000008) are xz streams from liblzma and now
decode; a bare .lzma stream is accepted too. The macOS fixture workflow
gains a `dmg_ulmo` variant (`hdiutil convert -format ULMO`), and the DMG
test covers it once the workflow has committed the fixture. The test
vector headers now split long hex into several string views, since clang
rejects a single literal above 64 K characters.

## Later: SquashFS reader

The tenth reader, and the first that exists because the decoders do:
SquashFS 4.0 with gzip (zlib), lzo (lzo1x), xz, lz4 (raw block), zstd
(frame) and lzma (.lzma) compressors, metadata blocks (2-byte header,
8 KiB, cached), inode table with basic and extended inodes of every type,
directory listings read whole (the index is not needed for a cold read),
fragment and id lookup tables, data blocks with the stored-uncompressed
flag, sparse blocks (size 0) as zeros and fragment tails. The last data
or fragment block is cached so a 400-file directory of fragment-packed
files does not decompress the same block 400 times. Inode ids are inode
references, so hard links share one id and `nlink` comes from the inode.
`lz4::decompressUpTo` was added for metadata blocks whose decompressed
size is only bounded.

Fixtures: `tools/fixtures/make_squashfs_fixtures.sh`, nine mksquashfs
images from one source tree (each compressor, uncompressed tables and
data, 64 KiB blocks with forced fragments, xz with the x86 BCJ filter,
which mksquashfs ends up not applying to this tree), checked by
`unsquashfs`; the oracle is the source tree. Live-system ISOs, snaps and
firmware images are now readable from inside any container.

## Later: APFS reader, with fixtures built on macOS

The container superblock (block 0, then the checkpoint descriptor area
for the newest valid copy by transaction id), Fletcher-64 verified on
every object, the container object map to the volume superblock, the
volume object map to the file system tree, and the APFS B-tree layout
(table of contents at the front, fixed or variable key/value sizes,
values growing from the back, root nodes with a trailing info block).
File system records: inodes with their extended fields (the data stream
size), directory records with hashed keys on case-insensitive volumes and
plain keys on case-sensitive ones, file extents by data-stream id with
sparse ranges, the `com.apple.fs.symlink` attribute for link targets. The
first volume opens; encrypted volumes and decmpfs-compressed files are
refused with `Unsupported`. One lesson from the first run: file system
tree keys sort by object id and then record type, not by the raw word
that keeps the type in its top four bits, so range descent must compare
the rotated form.

Fixtures come from `hdiutil create -fs APFS` on the macOS workflow
(case-insensitive and case-sensitive variants, the HFS+ tree plus an
xattr set with the `xattr` tool, since macOS's Python lacks
`os.setxattr`); both read back exactly against the mounted-tree oracle.
Eleven readers now: every filesystem a Linux, Windows or macOS system
disk, a camera card, an optical image, a live ISO or a VM disk is likely
to carry.

## Later: LZFSE decoder; DMG ULFO blocks

`compress::lzfseDecompress` and `lzvnDecompress` in `stein_core`: Apple's
stream of `bvx-` raw, `bvxn` LZVN and `bvx1`/`bvx2` FSE blocks up to
`bvx$`. The FSE part follows the reference closely: v2 headers with
packed fields and prefix-coded frequency tables, decoder tables built the
lzfse way (state counts 64/64/256/1024), literals from four interleaved
states and L/M/D triples from three, both read backwards from the end of
their payload with the input start as the only lower bound, the repeat
distance when D decodes to zero. Three things the reference taught in
the first run: the literal count is padded to a multiple of four with
bytes no match consumes, the backward streams legitimately load header
bytes on their first flush, and the L code's extra bits are 2/3/5/8.
LZVN is the opcode-driven small/medium/large/previous-distance scheme.
Vectors from Apple's encoder through the `lzfse` Python binding: inputs
that land in raw, LZVN, single and multi-block FSE form, plus truncation
and short buffers.

DMG `ULFO` blocks (0x80000007) now decode; the macOS fixture script gains
`dmg_ulfo` and the DMG test covers it once the workflow has committed the
fixture. Every DMG block type hdiutil produces is now readable.

## Later: EROFS reader

The twelfth reader, and the most intricate on-disk mapping so far.
Superblock, compact and extended inodes, flat plain and inline data,
chunk-based data with hole chunks, directories as 12-byte entries with a
name area per block. Compressed inodes follow erofs-utils' `zmap.c`
exactly: logical clusters described by 8-byte full indexes or by the
compacted 2-byte/4-byte packs (sixteen or two lclusters per pack with the
base block address in the pack's last word, the "last lcluster stores the
forward distance" rule, the alignment of the first 4-byte run), HEAD and
NONHEAD lclusters with lookback distances, big physical clusters whose
block count hides in the first NONHEAD index, tail packing (the last
pcluster inline after the indexes), fragments (file tails, or whole small
files, inside the packed inode, read through the same reader
recursively), dedupe references that need partial decoding, plain and
interlaced uncompressed pclusters. Algorithms: lz4 (with and without the
0-padding feature: without it the payload sits first and lz4 must stop at
the output size), MicroLZMA (the properties byte is stored inverted where
the range coder's zero byte would be), raw deflate, zstd. The decoders
gained "stop when the output is full" variants for the partial cases.

Fixtures: `tools/fixtures/make_erofs_fixtures.sh`, nine mkfs.erofs 1.7.1
images (uncompressed, chunk-based, lz4 compact and legacy indexes, lz4hc
with 64 KiB pclusters, ztailpacking, fragments plus dedupe with 16 KiB
pclusters, lzma, deflate), each checked by `fsck.erofs`; the oracle is
the source tree. Two mkfs quirks are documented in the script: it rejects
255-byte names, and in chunk mode it writes a sparse file as all holes.

## Later: macOS mount backend, an NFSv3 loopback server

The question was whether to build the macOS backend on FUSE (macFUSE, a
kext the user must allow on Apple Silicon; FUSE-T, proprietary) or on
"macOS's low-level block device API". The second does not exist in the
form one would want: there is no public way for a process to provide a
block device to the kernel (nothing like NBD, ublk or a userspace loop),
only `hdiutil attach` of a *file*, and a block device alone would help
only for filesystems macOS already drives. So the backend is the design
doc's plan: our own read-only NFSv3 server on 127.0.0.1 and the stock
`mount_nfs` with explicit `port`/`mountport`. No portmapper, no kext, no
admin rights, no third-party code, and it works on every macOS version.
The server is portable (POSIX and Winsock sockets), lives in
`stein_mount` on every platform, and speaks SunRPC with record marking,
MOUNT v3 (NULL, MNT, UMNT, EXPORT, DUMP) and NFS v3 (GETATTR, LOOKUP,
ACCESS, READLINK, READ, READDIR, READDIRPLUS, FSSTAT, FSINFO, PATHCONF;
every mutating call gets `NFS3ERR_ROFS`). File handles are the reader's
64-bit inode ids.

The block-device idea survives in a better form: `makeSingleFileReader`
exports a decoded or decrypted disk as one file over the same server, and
`stein attach` mounts that export and hands the file to `hdiutil attach
-imagekey diskimage-class=CRawDiskImage`, so macOS mounts HFS+, APFS,
exFAT, FAT, NTFS (read-only), UDF or ISO inside a LUKS, VeraCrypt, LVM,
qcow2 or E01 container with its own drivers. `stein serve` runs the server
standalone on any platform (`--raw` for the single-file export) and prints
the mount command for each OS. FSKit (macOS 15+) stays on the list for a
packaged app, since it needs a signed app extension.

Tests: a minimal SunRPC client in `test_mount` drives the server through
MNT, EXPORT, FSINFO, ACCESS, LOOKUP, READDIRPLUS, READ and READLINK on
every platform and compares the ext4 fixture tree with the kernel-mount
oracle; on macOS the existing mount test goes through `mount_nfs` and CI
requires it to succeed (`STEIN_REQUIRE_MOUNT=1` on all three systems now).
The one bug the real client found: the kernel sends AUTH_SYS credentials
and the RPC header parser read flavor and body in the wrong order, which
only AUTH_NULL survives; the test client now sends AUTH_SYS too. The
server also answers datagram RPC on the same port and can trace every
request (`STEIN_NFS_DEBUG=1`), which is how that bug was found from a CI
log. Unprivileged mounting works: `mount_nfs` runs as the user on the
GitHub macOS runner.

## Later: format versioning, raw images, and copying trees out of a reader

Three requests landed together: version the `.stein` format properly before
it grows, treat plain `dd`/GNOME Disks images as first-class on both the
input and the output side, and provide the primitive a "look inside without
mounting, drag files out" viewer needs.

**Versioning.** The header already had a `version` field (1) and 32 reserved
bytes. Bytes 96..115 now hold `version_minor`, three feature masks
(`compat`, `incompat`, `ro_compat`, ext4's model) and `writer_version`,
the libstein that wrote the segment packed as `(major << 16) | (minor << 8)
| patch`. The reader's policy is fixed in the spec and in code: a major it
does not know is refused with a message that names both versions ("format
2.x cannot be read by this libstein (0.1.0, format 1.1)"); a newer minor is
read, since minors only ever add fields in the reserved area or manifest
keys; an unknown `incompat` bit is refused and the error lists the bits and
the writer version ("written by libstein 2.3.4"); unknown `ro_compat` bits
open read-only, `compat` bits are ignored. Files from the 1.0 writer (every
image made before this change) have zeros in the new bytes and read as
1.0 with an unknown writer, which `stein image info` shows as such. The
manifest repeats `version_minor` and adds `"tool"`. The library's own
version comes from CMake (`STEIN_VERSION_*` defines from `project()`), so
`writer_version` cannot drift from the release number.

**Raw images.** `stein image create` writes a raw image when the target
ends in `.img`, `.raw` or `.dd` or `--format raw` is given (sparse, bad
sectors skipped as zeros, same progress and bad-sector policy as `.stein`),
and `stein image restore` accepts any container the probe recognises as the
source (raw, qcow2, VHD(X), VMDK, VDI, E01, DMG) and a file or device as
the target, creating a missing file. Opening raw images was already there;
the gap was writing them, which is what GNOME Disks and `dd` users
exchange.

**Copying trees out.** `fs::copyTree(reader, inode, hostPath, options,
progress)` copies a directory (or a file, or a symlink) out of any reader
onto the host filesystem: directories created, symlinks recreated, mtimes
preserved, a byte limit per file, per-entry warnings collected rather than
aborting (an unreadable file or an unrepresentable name skips that entry;
only host errors stop the copy), and a `Progress` for a UI. `stein cp` uses
it when the source is a directory. This is the "drag out" verb of the
viewer described in `doc/design/19-gui-brief.md`, which collects what the
libraries can do today (objects, operations, per-platform notes, error
model, suggested screens) in one document for designing a GUI.

Tests: header round trip and each refusal path in `test_image`; a full
ext4 fixture copied to the host and compared against the oracle tree
(names, types, sizes, link targets, contents) in `test_fs`.

## Later: the rest of VeraCrypt: Serpent, Twofish, Camellia, Kuznyechik, cascades, Whirlpool and Streebog

The VeraCrypt unlocker handled AES-XTS with four PRFs; this closes the
list. Four more 128-bit block ciphers live in `stein_core` behind one
`BlockCipher` interface (Serpent bitsliced with its S-boxes evaluated as
truth tables, Twofish with full keying, Camellia-256 per RFC 3713,
Kuznyechik per RFC 7801 with the S-box and linear layer folded into
tables), and a generic `crypto::Xts` replaces the AES-only one: one or more
layers, each with its own data and tweak key, applied in VeraCrypt's order
(the table lists "AES-Twofish"; encryption runs Twofish first, decryption
AES first). LUKS and the `XtsDevice` moved onto it unchanged in behaviour.
Two more hashes join `Hasher`: Whirlpool, built from the standard's three
mini-boxes rather than a copied table, and Streebog-512, kept little-endian
like the GOST reference implementations so message bytes load as they are;
HMAC and PBKDF2 come for free. PBKDF2 gained a ranged variant: its output
blocks are independent, so the unlocker derives the 64 bytes every single
cipher needs, and the other 128 (for two- and three-cipher cascades) only
when no single cipher opens the header, which keeps the common case as fast
as before while VeraCrypt itself always derives all 192.

Every cipher and hash is checked against an independent oracle (Botan for
Serpent, Twofish, Camellia, Whirlpool, Streebog and XTS; the GOST
`gostcrypto` package for Kuznyechik), including the published RFC/NESSIE
vectors, and the fixture generator writes eight more volumes: each new
cipher alone, the AES-Twofish-Serpent and Kuznyechik-Serpent-Camellia
cascades, Whirlpool and Streebog PRFs, and TrueCrypt volumes with Whirlpool
and the Serpent-Twofish-AES cascade. `stein tcrypt` takes `--prf` to skip
the trial over the other five PRFs; `TcryptInfo::cipher` now reads like
cryptsetup's ("serpent-twofish-aes-xts-plain64"). Two memory-vs-oracle
mismatches were caught by the vectors: Twofish's h-function had two of its
q-permutation stages swapped, and nothing else; the Serpent, Camellia,
Kuznyechik and Streebog constants were right first time, Kuznyechik's
S-box and Streebog's linear map having been cross-checked against the GOST
package's tables.
