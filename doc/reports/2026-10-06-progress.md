## Verified against the reference tools

- Our GPT writer reproduces `sgdisk`'s headers, entry arrays and protective
  MBR byte for byte (including the real CHS values sgdisk puts in the PMBR).
- Our MBR writer reproduces `sfdisk`'s MBR and EBR sectors byte for byte.
- After `stein repair` on an image with a zeroed primary header, `sgdisk -v`
  reports "No problems found".
- `stein pt dump` + `stein pt restore` brings a GPT with both headers
  destroyed back to a table sgdisk accepts — the R5a "restore only the
  table" scenario, 5 small regions instead of the whole disk.

## Design points settled while coding

- Tables are edited in memory; `write()` always places the backup at the
  end of the *target* device, which is what makes "restore to a larger disk"
  and "repair after growth" the same code path.
- `repair()` refuses to write when neither copy of the entry array is
  intact, rather than writing an empty table.
- Field tables come from manifests (`formats/*.layout.toml`); offsets appear
  exactly once. The generated classes are plain and debuggable.
- ASan caught one real bug during development (pointer into a vector that
  reallocated); sanitizers stay on in the debug preset and in Linux CI.

## Later the same day: `stein_fs` L0 landed

35 formats detected in-process with label, UUID, version, geometry and
clean/dirty state where the format has them: ext2/3/4, FAT12/16/32, exFAT,
NTFS (label from the `$Volume` MFT record, with update-sequence fixups),
ReFS, HFS/HFS+/HFSX (root folder name from the catalog B-tree, Apple's UUID
derivation, HFS wrapper descent), APFS container, XFS, btrfs, F2FS, JFS,
ReiserFS, Reiser4, NILFS2, bcachefs, OCFS2, Minix 1/2/3, EROFS, SquashFS,
swap, ISO 9660 + Joliet, UDF, ZFS, UFS, LUKS1/2, LVM2 PV (incl. VG name
from the text metadata), md RAID 1.x/0.90, BitLocker.

The test is an **oracle sweep**: 30 fixtures made with the real `mkfs`
tools (plus a synthesised md superblock that blkid validated), each with
`blkid -p -o export` recorded alongside; every TYPE, LABEL, UUID and VERSION
must agree. One finding: blkid reports nothing at all for an ext4 that is
marked not-cleanly-unmounted; we report it with a warning.

14 new manifests (`formats/*.layout.toml`) drive both the parsers and the
field trees; `stein fs <image> --doc` prints the annotated structures.

## Later still: probe tree, Linux platform, imaging

- **`stein_probe`**: the topology tree (table → partitions → contents,
  nested tables, free regions, cross-checks such as "filesystem larger than
  its partition"); `stein probe` renders it.
- **`stein_platform` (Linux)**: sysfs enumeration, raw devices with the
  BLK* ioctls, mounts, loop attach/detach; `stein list`; every command
  accepts `/dev/...`. Tested as root through a loop device.
- **`stein_image`**: the `.stein` container v1 (`doc/spec/stein-image-v1.md`),
  copy engine with zero detection and a bad-sector policy, LZ4 block codec
  and a JSON module in core, operations create/restore/verify/info/open.
  `stein image create /dev/sdb out.stein` records the probe topology in the
  manifest; `stein probe out.stein` then shows the image exactly like the
  disk (R5d). A 16 MiB test disk becomes a 15 KB image; restore is
  byte-identical; corruption is reported per chunk; a crashed write (no
  trailer) is recovered by scanning.
- CI runs on Linux, macOS and Windows; Linux and macOS are green, Windows
  is being brought up (MSVC strictness: missing includes, narrowing).
