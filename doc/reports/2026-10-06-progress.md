## Verified against the reference tools

- Our GPT writer reproduces `sgdisk`'s headers, entry arrays and protective
  MBR byte for byte (including the real CHS values sgdisk puts in the PMBR).
- Our MBR writer reproduces `sfdisk`'s MBR and EBR sectors byte for byte.
- After `stein repair` on an image with a zeroed primary header, `sgdisk -v`
  reports "No problems found".
- `stein pt dump` + `stein pt restore` brings a GPT with both headers
  destroyed back to a table sgdisk accepts — the R5a "restore only the
  table" scenario, 5 small regions instead of the whole disk.

## Design points settled while coding

- Tables are edited in memory; `write()` always places the backup at the
  end of the *target* device, which is what makes "restore to a larger disk"
  and "repair after growth" the same code path.
- `repair()` refuses to write when neither copy of the entry array is
  intact, rather than writing an empty table.
- Field tables come from manifests (`formats/*.layout.toml`); offsets appear
  exactly once. The generated classes are plain and debuggable.
- ASan caught one real bug during development (pointer into a vector that
  reallocated); sanitizers stay on in the debug preset and in Linux CI.

## Later: `stein_ops` — plan, preview, apply on the real code path

The design in `design/13-operations.md` said the preview should not be a
parallel model of what the jobs *would* do. It now is not: `OverlayDevice`
(`stein_block`) is a copy-on-write device over the target; an
`OperationStack` runs each operation's jobs against the overlay and
re-probes the overlay for the preview. `apply()` writes the overlay's dirty
blocks to the device in one ordered pass, re-probes, and reports whether the
device matches the preview. A failing job rolls the overlay back; `pop()`
replays the remaining operations on a fresh overlay.

Operations so far: `CreateTable` (GPT/MBR/APM; zeroes old table copies and
whole-device filesystem signatures first), `AddPartition` (optionally wipes
stale signatures in the new range), `DeletePartition`, `UpdatePartition`
(type/name/bounds), `RepairTable`, `WipeSignatures`. `signatureRegions()`
derives what to zero from the probe tree (first MiB, every metadata region
the detectors reported, last MiB).

CLI: `stein pt create|add|rm|set|wipe`, each printing the pending list, the
bytes it would touch and the resulting tree; `--dry-run` stops there,
destructive edits on a real block device need `--force`. A create/add/set
sequence on a 64 MiB image gives a table `sgdisk -v` finds no problems with.

Windows CI: compiles; the remaining failure was DLLs not found by the test
executables (fixed by one `bin/` output directory).

## Later: three platforms, split images, pieces, and dr_stein v2's core

- **CI is green on Linux, macOS and Windows.** The Windows failures were
  MSVC strictness, DLL placement (all runtime outputs now land in one `bin/`
  directory) and `remove_all` on files still open; none were logic bugs.
- **Platform backends** for macOS (IOKit `IOMedia` enumeration, `/dev/rdiskN`
  with the DKIOC ioctls, `getmntinfo`, `hdiutil attach`) and Windows
  (`PhysicalDriveN`, `STORAGE_QUERY_PROPERTY`, drive geometry and access
  alignment, drive letter → disk extents, `IOCTL_DISK_UPDATE_PROPERTIES`,
  Administrators check). Both raw-device classes derive from
  `AlignedDevice`, which turns arbitrary reads and writes into sector-aligned
  I/O with a bounce buffer; that logic is unit-tested on Linux against a fake
  device that rejects unaligned I/O, so the part that cannot be tested in CI
  without real disks is reduced to thin OS calls.
- **Split raw images** (`disk.img.000`, `.001`, …) open as one device through
  `ConcatDevice`; the CLI accepts them wherever an image is taken.
- **Filesystem header pieces**: `stein fs dump <image> <piece> [--part N]` and
  `stein fs restore` save and restore a filesystem's identification regions
  (superblock/boot sector, descriptor tables, backups) the same way `pt
  dump/restore` does for tables (R5a).
- **`stein_app`**: `Profile` (JSON) names a target by serial/WWN/model/size
  with a tolerance, a path only as a locked fallback, an image location and
  format, and a policy (lock, elevation, smaller targets, verification
  levels). `resolveTarget()` finds exactly one disk and refuses ambiguity;
  `status()` says whether Backup and Restore are "ready"; `backup`, `restore`
  and `verify` compose the image operations with a `Report`, verify the image
  before writing, read the target back against the image's SHA-256 afterwards,
  and move the GPT backup to the end of a larger target. `stein app
  init|status|backup|restore|verify` is the whole dr_stein v2 workflow on the
  command line; a GUI only has to render `describe(profile, status)` and two
  buttons.
- **Hashing fast paths**: slice-by-8 CRC tables, hardware CRC32C (SSE4.2 /
  ARMv8 CRC) and SHA-256 (SHA-NI / ARMv8 SHA-2) with runtime detection and a
  cross-check test over every length and alignment (`STEIN_NO_SIMD=1`
  disables them). Release build, 1 GiB file with 256 MiB of random data,
  page-cached, 4-core Xeon:

## Later: used-block-only imaging (L1)

`fs::AllocationMap` plus `FileSystem::allocationMap()` for ext2/3/4 (group
descriptor block bitmaps), FAT12/16/32 (FAT entries), exFAT (allocation
bitmap file through the root directory), NTFS (`$Bitmap` via the MFT run
list) and HFS+ (allocation file extents). Dirty filesystems and ext journals
needing recovery refuse, so a stale bitmap never drops data. The copy engine
zeroes free blocks of mapped filesystems, so whole-free chunks become zero
chunks and partially used chunks compress to their used part; the manifest
records `used_blocks_only`. `stein image create --used-only`, and profiles
default to it (`image.used_only`).

Fixtures `tests/fixtures/alloc/` are real `mkfs` outputs with files written
through loop mounts; the test asserts that **every non-zero byte on the
device lies in a block the map calls used** and that free counts equal
`dumpe2fs`, `fsck.fat` and `ntfsinfo`. On a 64 MiB ext4 with 8 MiB of junk in
free space, the image went from 8.5 MB to 140 KB, `e2fsck -fn` is clean after
restore and the files' checksums match.

## Later: encrypted images (R5e)

`stein_core` gained ChaCha20-Poly1305, HMAC-SHA256, PBKDF2-HMAC-SHA256 and OS
randomness (own code; known-answer vectors from the Python `cryptography`
package and RFC 8439; tamper tests). `.stein` images can now be encrypted:
a plaintext key area with up to eight passphrase slots wraps one random
master key (LUKS2 shape, `doc/spec/stein-image-v1.md` §Encryption); the
manifest, every chunk and the image hash are protected, while structure and
per-chunk stored CRCs stay verifiable without the key. `stein image create
--passphrase`, `stein image keys list|add|remove`, `--passphrase`,
`--passphrase-file`, `$STEIN_PASSPHRASE` or a no-echo prompt everywhere an
image is opened; profiles set `image.encrypt` and never store the passphrase.
Decision D16 records why ChaCha20-Poly1305 and not AES-GCM/XTS.

Also since the last section: `Platform::unmount()` on Linux/macOS, Windows
volume lock + dismount on exclusive open, and the restore scenario unmounts
or refuses while the target's volumes are mounted.

## Later: encrypted pieces and media tests

- `pt dump`/`fs dump` pieces are encrypted with the same key area when a
  passphrase is given (`STEINPIECE1E`); `stein::Keys` moved to `stein_core`.
- `stein media scan` (read-only surface scan) and `stein media test`
  (destructive fake-flash capacity test): a keyed pattern carrying its own
  offset is written across the device; on read-back, chunks holding another
  address's pattern reveal address wraparound and the gcd of the
  displacements is the real capacity; sticks that drop writes show as
  "pattern stops at X". Tested with simulated wrapping and dropping sticks.

## Later: LUKS opened in-process (the flagship goal's first half)

`stein_container` parses LUKS1 and LUKS2 headers, unlocks a key slot with a
passphrase (PBKDF2 with sha256/sha1 or Argon2id/Argon2i, AES-XTS-decrypted
key material, anti-forensic merge, master-key digest check) and presents
the payload as a `BlockDevice` that decrypts per sector (aes-xts-plain64,
512 or 4096-byte sectors, `iv_tweak`). AES comes with AES-NI and ARMv8
kernels. Fixtures were formatted by `cryptsetup` and their payload encrypted
by the Python `cryptography` package under the dumped master key, so the
test compares our recovered master key with cryptsetup's and probes the
inner ext2. `stein probe --passphrase` shows the plaintext under the
container; `stein luks info|unlock|extract` inspect, check and decrypt into
a plain image, on any OS: this is the step before mounting an ext4-in-LUKS
on Windows or macOS.

## Later: LVM2 logical volumes (the other half of "ext4 in LVM in LUKS")

`stein_volume` reads a PV's text metadata (including the wrapped circular
buffer), parses LVM's config grammar into a volume group model and
assembles logical volumes as devices: linear and multi-segment volumes via
slices and `ConcatDevice`, striped volumes via a round-robin
`StripedDevice`; mirror/raid/thin/cache segments are reported, not mapped.
PVs are added one by one; a volume maps once every PV it touches has been
seen. Fixtures come from lvm2 itself (`--driverloaded n`, no activation),
with filesystems written at the extent offsets `lvs` reports, so the test
reads `lv_linear`, `lv_frag` (two segments) and `lv_striped` (two PVs) back
through our mapping. `stein probe` lists a PV's volumes and probes the
mappable ones; `stein lvm list|extract` shows the group and copies a volume
into a plain image.

## Later: reading files in-process (L3 for ext2/3/4)

`fs::Reader` (root, lookup, stat, readdir, read, readlink) and an ext2/3/4
implementation: extent trees and indirect blocks, inline data, linear /
htree / inline directories, fast and slow symlinks, hard links, holes,
64-bit descriptors, 1/2/4 KiB blocks. The fixtures are kernel-mounted
images with deterministic content; the test walks the whole tree and
compares every entry, every file's SHA-256 and every symlink target with
the mount. `stein ls|cat|cp` read through partitions (`--part`), LUKS
containers (`--passphrase`) and LVM volumes (`--lv`): an ext4 inside LVM
inside LUKS is now browsable on any OS without a kernel driver, which is
the read half of the vision's R6.

## Later: NTFS reader

The same `fs::Reader` interface over NTFS: MFT records with fixups and
attribute lists, resident and non-resident `$DATA` through run lists
(sparse runs, initialized size), directories from `$INDEX_ROOT` and the
in-use INDX blocks of `$INDEX_ALLOCATION`, Win32/POSIX names (DOS aliases
skipped), hard links, reparse-point and ntfs-3g Interix symlinks,
case-insensitive lookup; compressed and EFS-encrypted data are refused with
a clear error. Fixture written through an ntfs-3g mount with Unicode and
200-character names, a 300-entry directory, a sparse file and links; every
entry and SHA-256 matches. Windows system disks are therefore browsable
from Linux and macOS without a kernel driver.

## Later: FAT12/16/32 reader

Cluster chains through the FAT, fixed and chained root directories, long
file names (UTF-16, checksum-validated with 8.3 fallback and case flags),
DOS timestamps, case-insensitive lookup. The kernel here has no vfat
driver, so the fixtures were written with the `pyfatfs` package
(`tools/fixtures/make_fat_fixtures.py`) and the oracle is the content we
wrote; `fsck.fat` confirms the images are clean. Three in-process readers
(ext, NTFS, FAT) now cover the filesystems a dr_stein restore stick meets.

## Later: mounting any reader through FUSE (R5d on Linux)

`stein_mount`: an `fs::Reader` becomes a read-only filesystem the OS can
browse. The Linux backend is libfuse3 (LGPL, linked dynamically, optional
at configure time: without `pkg-config fuse3` a stub reports
`Unsupported`). High-level FUSE operations getattr/readdir/open/read/
readlink/statfs over a path → inode cache, one thread, no writes
(`EROFS`), `allow_other` on request. `stein mount <image|device> <dir>
[--part N] [--passphrase ...] [--lv NAME]` mounts a partition from inside
an image, a LUKS container or an LVM volume the same way `stein ls` reads
it; `fusermount3 -u` or `umount` ends the loop cleanly, and `Mount::stop()`
does the same from inside a program. The test mounts the ext4 fixture
in-process and compares every file hash, directory and symlink with the
kernel-mount oracle through plain `std::ifstream` /
`std::filesystem` calls, then checks that creating a file fails.

One real lesson is encoded in `stop()`: `fuse_exit()` alone does not wake
a loop blocked in `read()`, and libfuse drops a request it reads after
the exit flag is set, so a process that pokes its own mountpoint to wake
the loop deadlocks in the kernel for good (uninterruptible, only
`/sys/fs/fuse/connections/*/abort` frees it). Unmounting is the only
clean wake-up; the loop then ends with `ENODEV`, which libfuse treats as
a normal exit.

macOS and Windows build the stub for now; the kext-less NFS loopback /
WinFsp-or-Dokany backends from design doc 15 are the next step there.

## Later: exFAT reader

Boot-sector geometry, 32-bit FAT chains and contiguous `NoFatChain`
streams, directory entry sets (File + Stream Extension + File Name),
`ValidDataLength`-aware reads, timestamps with their UTC-offset byte, and
case-insensitive lookup through the volume's own (run-length compressed)
up-case table, so `ünïcödé` matches `ÜNÏCÖDÉ` the way the format defines
it. The container has no kernel exfat driver, so the fixtures are written
with exfat-fuse over a loop device (`tools/fixtures/make_exfat_fixtures.sh`,
4 KiB and 32 KiB clusters, a deliberately fragmented file, 255-character
and Unicode names, a 300-entry directory) and checked by `fsck.exfat`;
every entry, size and SHA-256 matches. `resolvePath` now keeps an ancestor
stack for `..` instead of expecting a dot-dot directory entry, which exFAT
(like NTFS and HFS+) does not have. Four readers (ext, NTFS, FAT, exFAT)
cover every filesystem a camera card, a USB stick or a Windows or Linux
system disk is likely to carry; all of them mount through `stein mount`.

## Later: HFS+ / HFSX reader, with fixtures built on macOS

The fixture problem first: the Debian `hfsplus` tools reject volumes made
by `mkfs.hfsplus` and there is no kernel driver in the build container, so a
small workflow (`.github/workflows/fixtures-macos.yml`) builds the images on
the macOS runner with `hdiutil` and the native driver, fills them with the
same deterministic tree as the other readers plus hard links and names that
differ only in case, records the oracle with a portable `oracle.py`, and
commits the result to the branch (artifact downloads are blocked from some
environments). Three variants: HFS+, case-sensitive HFSX and journaled HFS+.

The reader (TN1150): volume-header forks, B-tree header/index/leaf nodes,
catalog folder, file and thread records, the extents overflow tree for forks
with more than eight extents, hard links resolved through the `iNode` files
in the private metadata folder (link counts included), `S_IFLNK` symlinks,
the journal files and private folders hidden the way the kernel hides them,
case-insensitive lookup for HFS+ and binary for HFSX. Catalog searches use
only the parent-id part of the key order, so no copy of Apple's case-folding
table is needed for listings; the test compares every entry, SHA-256,
symlink target, the hard-link count of three and the stored mtime for all
three variants. Five readers now: ext, NTFS, FAT, exFAT, HFS+.

## Later: ISO 9660 reader

Primary and supplementary volume descriptors, directory records with
both-endian fields and multi-extent files, Rock Ridge SUSP entries (`SP`,
`CE` continuation areas, `NM` names, `PX` modes and link counts, `SL`
symlinks with split components, `TF` timestamps, `CL`/`RE` deep-directory
relocation presented the way the kernel does) and Joliet UCS-2 names; the
name source is Rock Ridge, else Joliet, else plain ISO with the `;1`
version stripped. Fixtures come from `genisoimage` in three flavours
(`tools/fixtures/make_iso_fixtures.sh`); `isoinfo` is the oracle for the
plain image, the source tree for Rock Ridge and Joliet (isoinfo cannot
print CJK Joliet names, and it does not follow relocation, so the Joliet
oracle is cross-checked against `isoinfo -f -J` for every ASCII path).
Six readers: ext, NTFS, FAT, exFAT, HFS+, ISO 9660.

## Later: VeraCrypt and TrueCrypt volumes

`container::Tcrypt` opens VeraCrypt and TrueCrypt volumes the only way the
format allows: there is no signature, so each candidate header (primary,
hidden at 64 KiB, and the two backup copies at the end) is decrypted with
the passphrase through PBKDF2-HMAC-SHA-512 or SHA-256 (VeraCrypt, with the
PIM iteration multiplier; TrueCrypt's 1000-iteration SHA-512) and AES-XTS,
and accepted when the magic and both CRC-32s check out. The payload is the
same XTS device LUKS uses, with the absolute 512-byte data-unit number as
tweak. SHA-512 joined the core hashes for this, and the generic HMAC/PBKDF2
is now allocation-free (the 500 000-iteration default takes well under a
second in release). Cheap headers are tried first, so a TrueCrypt probe
never pays VeraCrypt's price. Fixtures are generated by an independent
Python implementation of the format (`cryptography` XTS, hashlib PBKDF2)
around debugfs-filled ext2 payloads: default-PIM SHA-512, SHA-256 with PIM
3, TrueCrypt, and an outer+hidden pair; the test opens each, reads the file
inside, rejects a wrong passphrase, and opens the volume from its backup
header after the primary one is overwritten. `stein probe --passphrase`
now descends into such volumes, `stein ls|cat|cp|mount` read through them,
and `stein tcrypt unlock|extract` work like their LUKS counterparts.
Cascades (Serpent, Twofish, Camellia, Kuznyechik), the other PRFs and
system encryption are reported as unsupported rather than guessed at.

## Later: XFS reader

Superblock geometry, v2/v3 inodes with `bigtime` and `nrext64` handled,
data forks in local, extents and B+tree form (the bmbt root inside the
inode, `BMAP`/`BMA3` blocks on disk), directories in shortform, block,
leaf and node form (the data blocks below the 32 GiB leaf offset are all a
listing needs), inline and remote symlinks, holes and unwritten extents as
zeros. Fixtures are built by `mkfs.xfs -p protofile`, which populates a
filesystem without a kernel driver (`tools/fixtures/make_xfs_fixtures.sh`:
4 KiB and 1 KiB blocks, a 300-entry leaf directory and a 700-entry node
directory, Unicode and 255-byte names), verified by `xfs_repair -n`; the
oracle is the source tree. Seven readers: ext, NTFS, FAT, exFAT, HFS+,
ISO 9660, XFS. btrfs is next (`mkfs.btrfs --rootdir` gives fixtures the
same way).
